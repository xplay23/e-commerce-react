# Совместимость двух магазинов

Проверены SQL-схема, PHP маршруты, bootstrap, Vue API-клиент и сервисы исходного проекта `D:\work\e-commerce`.

| Данные | Существующий контракт | React |
| --- | --- | --- |
| Товары и категории | `GET categories`, `GET products`, `GET products/{slug}` | Использует те же ID, slug, фильтры; пагинация по 12 |
| Пользователи | `POST auth/register`, `POST auth/login`, `GET auth/me` | Тот же users и PHP password_hash/password_verify; клиент не обрабатывает хеши |
| Сессии | Bearer token; SHA-256 в auth_tokens; TTL из backend/.env | Тот же серверный формат; отдельный ключ localStorage nord-react-auth-token |
| Избранное | GET/POST/DELETE favorites; product_id; уникальность user_id/product_id | Сохраняется в общей таблице, доступно с обоих фронтендов после обновления |
| Админка | GET/POST admin/products; PUT admin/products/{id}; requireAdmin | Те же поля и роли; скрытие через is_active=false вместо физического удаления |
| Заказы | POST orders; GET orders | Отправляет только ID и количество плюс контакты; цены и остатки вычисляет PHP |
| Валюта | Исходный Vue форматирует цены как USD; в схеме нет валюты | Сохранён USD; числовые значения не конвертируются |

## Почему схема не конфликтует

Vue использует исходный PHP backend, React — его копию в /e-commerce-react/backend/public/api. Обе копии должны быть настроены на одну MySQL-базу через backend/.env. Код обработки данных сохранён; дальнейшие изменения PHP API необходимо синхронизировать в обеих копиях. React не содержит SQL, миграций, seed, второго механизма авторизации или прямого доступа к БД. Nullable поля и boolean-флаги админки отправляются в формате, ожидаемом существующим PHP API. Bigint ID остаются строками, без потери точности JavaScript.

Корзина хранится отдельно в браузере (`nord-react-cart`); на сервере нет таблицы корзин. Учётные записи и избранное общие, а сессии и корзины между разными origin браузера автоматически не синхронизируются. Изменения товаров видны после повторного запроса/обновления страницы; подписок на изменения в исходном backend нет.

## Найденные ограничения исходного backend

- CORS допускает только один FRONTEND_URL. React работает на порту 5174 через same-origin Vite proxy, Vue может оставаться на 5173. В production React обращается к своей копии API на том же домене b-m.work, поэтому CORS для него не требуется.
- Редактирование товара — полная замена полей через PUT. Одновременные изменения двух администраторов используют правило «последняя запись выигрывает»; optimistic locking отсутствует. React не может гарантировать отсутствие потерянных изменений без доработки общего API.
- Создание заказа использует транзакцию и SELECT FOR UPDATE, защищая остатки при заказах из разных проектов. При этом исходный API не объединяет повторяющиеся product_id в одном запросе: такой сторонний запрос может нарушить проверку остатков. React отправляет одну строку на товар.
- API не поддерживает idempotency-key для заказов. React блокирует повторный submit, но после сетевого таймаута невозможно надёжно определить, был ли заказ создан. Для гарантии нужна доработка общей серверной логики.
- Конфликт уникального slug в админке возвращается исходным API как общая ошибка БД (500). React показывает ошибку и сохраняет открытый редактор.
- product_images есть в схеме, но API всегда возвращает images=[] и редактирует только image_url. React использует основное изображение.
- В исходном .env.local есть устаревшая настройка Supabase, но текущие Vue-сервисы используют PHP API, а не Supabase. В React она не переносится.

Исходный backend и данные не изменялись; в React-проект добавлена копия backend и правила Apache для подпапки. Сборка и локальные контрактные тесты не подтверждают фактическую доступность MySQL: это отдельно проверяет `node scripts/check-api.js` на запущенном API.
